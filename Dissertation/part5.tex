\section{Назначение прототипа}

Разработанный программный прототип предназначен для экспериментальной проверки гибридного метода управления ресурсами в распределённой edge-среде. Его задача состоит не в воспроизведении промышленной платформы исполнения задач, а в построении исследовательской симуляционной среды, в которой могут быть реализованы и сопоставлены все ключевые элементы модели, введённой в главах~2--4: поток задач от устройств, сеть периферийных узлов, аукционное распределение, VCG-платежи, локальные действия агентов и обучение координированной политики.

Прототип реализует двухконтурную архитектуру метода MA--VCG--QMIX. Первый контур отвечает за экономически интерпретируемое распределение задач на основе максимизации социального благосостояния в отдельном раунде~\cite{patent_ma_vcg}. Второй контур реализует многоагентную адаптивную политику, которая использует аукционный контекст при выборе локальных действий и обучается в условиях изменяющейся нагрузки, неоднородности ресурсов и возможных отказов узлов.

\section{Архитектура программной реализации}

Программная реализация построена модульно и разделена на несколько логических подсистем:
\begin{itemize}
	\item \texttt{src/environment} --- симуляционная среда: устройства, задачи, edge-узлы и основной класс среды;
	\item \texttt{src/mechanisms} --- аукционный слой: функции полезности и стоимости, вычисление распределения и VCG-платежей;
	\item \texttt{src/agents} --- нейросетевые компоненты QMIX;
	\item \texttt{src/learning} --- обучение, формирование вознаграждения, выполнение симуляционного цикла и многосидовый benchmark-контур;
	\item \texttt{main\_run\_all\_scenarios.py} --- воспроизводимая точка входа для полного набора вычислительных экспериментов;
	\item \texttt{experiments/results} --- сохраняемые артефакты вычислительных экспериментов: пошаговые логи, сводные таблицы и агрегированные метрики;
	\item \texttt{visualization} --- построение таблиц и графиков по сохранённым результатам;
	\item \texttt{tests} --- модульные и интеграционные тесты.
\end{itemize}

Такое разделение соответствует структуре самого метода. Среда отвечает за динамику состояния, аукционный модуль --- за статическое распределение задач в пределах одного слота, а обучаемый контур --- за последовательное принятие решений. \section{Модель предметной области}

Базовой сущностью симуляции является задача \texttt{Task}. Она содержит идентификатор устройства-источника, требования к CPU и памяти, объём входных данных, дедлайн, приоритет и важность устройства. В актуальной реализации в задаче дополнительно хранятся коэффициенты базовой ценности, а также служебные поля, заполняемые в аукционном контуре: назначенный узел, рассчитанный платёж, вклад в социальное благосостояние и оценка сетевой задержки.

\begin{lstlisting}[language=Python,caption={Модель вычислительной задачи},label={lst:task-model}]

class Task:

    device_id: int

    memory_required: int

Периферийный узел \texttt{EdgeNode} хранит доступные ресурсы, очередь ожидающих задач, множество исполняемых задач и состояние отказа. На каждом шаге узел сначала обновляет время выполнения уже запущенных задач, освобождает ресурсы для завершённых задач, а затем выбирает из очереди новые задачи в порядке приоритета и дедлайна.

\begin{lstlisting}[language=Python,caption={Обновление состояния edge-узла},label={lst:edge-node-step}]
def step(self, current_time: int, step_duration_ms: int):
    self.update_failure_state(current_time)
    if self.is_failed:
        return [], []

    completed_tasks = []
    latencies_ms = []
    for task_id in list(self.task_executed.keys()):
        self.task_executed_time[task_id] -= 1
        if self.task_executed_time[task_id] <= 0:
            completed_task = self.task_executed[task_id]
            latency_ms = max(
                0.0,
                (current_time - completed_task.arrival_time + 1)
                * step_duration_ms,
            )
            latencies_ms.append(latency_ms)
            completed_tasks.append(completed_task)
            self._completed_task(completed_task)

    sorted_queue = sorted(
        self.task_queue.values(),
        key=lambda task: (-task.priority.value, task.deadline, task.id),
    )
    for task in sorted_queue:
        if self._can_allocate_task(task):
            self._allocate_task(task, step_duration_ms)

    return completed_tasks, latencies_ms
\end{lstlisting}

\section{Симуляционная среда}

Центральным классом прототипа является \texttt{EdgeComputingSystem}. При инициализации он создаёт множество устройств, множество edge-узлов и граф сетевой топологии. В графе присутствуют вершины двух типов --- устройства и вычислительные узлы --- а веса рёбер интерпретируются как сетевые задержки. Задачи генерируются по пуассоновскому потоку, интенсивность которого может дополнительно модулироваться во времени и усиливаться кратковременными всплесками.

Важной особенностью текущей реализации является двухфазная организация одного шага симуляции. Сначала среда подготавливает аукционный раунд: обновляет состояние отказов, формирует пул задач, вычисляет матрицы полезности и стоимости, запускает MA--VCG и строит расширенные наблюдения агентов вместе с масками допустимых действий. Только после этого агенты выбирают действия, и среда применяет их к уже подготовленному раунду.

\begin{lstlisting}[language=Python,caption={Подготовка аукционного раунда},label={lst:prepare-round}]
def _ensure_round_prepared(self):
    if self._pending_round is not None:
        return

    self.current_time += 1
    self._update_node_failures()
    self.tasks = {}

    self._generate_tasks()
    utility_matrix, cost_matrix = self._evaluate_tasks()
    task_vector = self._build_task_vector()

    auction_result = self.auctioneer.run_auction(
        utility_matrix,
        cost_matrix,
        tasks=task_vector,
        nodes=self.nodes,
    )
    action_masks = self._build_action_masks(auction_result.allocation)
    auction_features = self._build_auction_features(
        allocation=auction_result.allocation,
        payments=auction_result.payments,
    )
    observations = self._compose_observations(
        action_masks,
        auction_features,
    )
\end{lstlisting}

После выбора действий агентами среда исполняет шаг: задачи либо принимаются к исполнению, либо отклоняются, затем обновляются очереди, фиксируются завершённые задачи и рассчитываются итоговые метрики.

\begin{lstlisting}[language=Python,caption={Основной шаг симуляционной среды},label={lst:environment-step}]
def step(self, actions: List[int]):
    self._ensure_round_prepared()
    pending_round = self._pending_round

    accepted_tasks, rejected_tasks, assignments, \
    realized_allocation, realized_payments = self._distribute_tasks(
        pending_round["auction_result"].allocation,
        pending_round["auction_result"].payments,
        pending_round["utility_matrix"],
        pending_round["cost_matrix"],
        actions,
    )

    completed_tasks, latencies = self._execute_tasks()
    rewards = self._compute_rewards(
        accepted_tasks=accepted_tasks,
        rejected_tasks=rejected_tasks,
        completed_tasks=completed_tasks,
        realized_payments=realized_payments,
        utility_matrix=pending_round["utility_matrix"],
        cost_matrix=pending_round["cost_matrix"],
        realized_allocation=realized_allocation,
    )
\end{lstlisting}

\section{Оценка полезности и стоимости}

Для каждой допустимой пары <<задача--узел>> среда строит две матрицы: матрицу полезности $U$ и матрицу стоимости $C$. Полезность рассчитывается как базовая ценность задачи, умноженная на дисконт по задержке, за вычетом затрат энергии на передачу данных. Базовая ценность представлена как взвешенная линейная функция требований к CPU и памяти, умноженная на приоритет и важность устройства. Задержка учитывает как ожидаемое время обработки на узле, так и сетевой путь между устройством и узлом.

Стоимость узла складывается из трёх частей: вычислительной стоимости, коммуникационной стоимости и нелинейной перегрузочной компоненты. Последняя отражает рост издержек при приближении узла к насыщению по CPU и памяти и реализована в квадратичной форме.

\begin{lstlisting}[language=Python,caption={Расчёт полезности и стоимости задачи},label={lst:evaluation}]
def evaluate_utility(task, edge_node, network_latency_ms=0.0):
    weighted_demand = (
        task.utility_cpu_weight * task.cpu_required
        + task.utility_memory_weight * task.memory_required
    )
    base = (
        task.utility_scale
        * task.priority.value
        * task.importance
        * weighted_demand
    )

    estimated_time_ms = (
        task.processing_time_ms(edge_node.cpu_capacity)
        + max(network_latency_ms, 0.0)
    )
    time_penalty = math.exp(
        -edge_node.delay_sensitivity
        * estimated_time_ms
        / max(task.deadline, 1.0)
    )

    energy_cost = (
        task.data_size
        * max(network_latency_ms, 0.0)
        * edge_node.transmission_energy_coeff
    )
    return max(base * time_penalty - energy_cost, 0.0)

def evaluate_cost(task, edge_node, network_latency_ms=0.0, direct_connection=True):
    computation_cost = (
        task.cpu_required * edge_node.base_price["CPU"]
        + task.memory_required * edge_node.base_price["MEM"]
    )
    path_penalty = 1.0 if direct_connection else edge_node.indirect_link_penalty
    communication_cost = (
        network_latency_ms
        * task.data_size
        * edge_node.base_price["NET"]
        * path_penalty
    )
    overload_cost = (
        edge_node.overload_cpu_weight
        * (
            (edge_node.cpu_used + task.cpu_required)
            / (edge_node.cpu_capacity + edge_node.overload_epsilon)
        ) ** 2
        + edge_node.overload_memory_weight
        * (
            (edge_node.memory_used + task.memory_required)
            / (edge_node.memory_capacity + edge_node.overload_epsilon)
        ) ** 2
    )
    return computation_cost + communication_cost + overload_cost
\end{lstlisting}

\section{Аукционный механизм MA--VCG}

Аукционный слой реализован классом \texttt{VCGAuctioneer}. На вход он получает матрицы полезности и стоимости, а также состояние задач и доступных ресурсов узлов. На выходе формируются бинарная матрица распределения, вектор платежей и значение социального благосостояния.

В актуальной версии прототипа распределение задач строится не жадной эвристикой, а точной процедурой поиска типа branch-and-bound с допустимой верхней оценкой для отсечения нерентабельных ветвей. Такой выбор важен для исследовательских сценариев малой и средней размерности, поскольку позволяет сделать программную реализацию согласованной с теоретическими утверждениями главы~2 о статической эффективности раунда при точном решении задачи выбора победителей. В ходе подготовки экспериментальной главы именно этот фрагмент был дополнительно оптимизирован: поиск упорядочивает устройства по их наилучшему чистому вкладу и сначала рассматривает наиболее перспективные размещения, что заметно сокращает время полного benchmark-прогона.

\begin{lstlisting}[language=Python,caption={Точное распределение задач с ограничениями ресурсов},label={lst:exact-allocation}]
best_score = 0.0
best_choices = np.full(m, -1, dtype=int)
current_choices = np.full(m, -1, dtype=int)
cpu_state = list(remaining_cpu)
memory_state = list(remaining_memory)

def search(idx: int, current_score: float) -> None:
    nonlocal best_score, best_choices
    if idx >= len(ordered_devices):
        if current_score > best_score + 1e-9:
            best_score = current_score
            best_choices = current_choices.copy()
        return

    if current_score + best_future_gain[idx] <= best_score + 1e-9:
        return

    device_id = ordered_devices[idx]
    for node_id, net_value, cpu_req, mem_req in device_options[device_id]:
        if cpu_state[node_id] < cpu_req or memory_state[node_id] < mem_req:
            continue
        current_choices[device_id] = node_id
        cpu_state[node_id] -= cpu_req
        memory_state[node_id] -= mem_req
        search(idx + 1, current_score + net_value)
        memory_state[node_id] += mem_req
        cpu_state[node_id] += cpu_req
        current_choices[device_id] = -1

    search(idx + 1, current_score)
\end{lstlisting}

VCG-платёж интерпретируется как внешний эффект присутствия участника на остальных агентах системы. 

\begin{lstlisting}[language=Python,caption={Расчёт VCG-платежа как внешнего эффекта},label={lst:vcg-payment}]
for i in range(m):
    if allocation[i].sum() == 0:
        continue

    allocation_without_i = self._compute_optimal_allocation(
        utility_matrix,
        cost_matrix,
        tasks=tasks,
        nodes=nodes,
        excluded_device=i,
    )
    sw_without_i = self.compute_social_welfare(
        utility_matrix,
        cost_matrix,
        allocation_without_i,
    )

    chosen_nodes = allocation[i].astype(bool)
    current_contribution = float(
        np.sum(
            np.asarray(utility_matrix[i], dtype=float)[chosen_nodes]
            - np.asarray(cost_matrix[i], dtype=float)[chosen_nodes]
        )
    )
    payments[i] = max(
        0.0,
        sw_without_i - (current_sw - current_contribution),
    )
\end{lstlisting}

\section{Расширенные наблюдения и действия агентов}

Многоагентный слой использует не только базовые характеристики локального состояния узла, но и аукционный контекст. Базовая часть наблюдения включает долю доступного CPU, долю доступной памяти, нормированную длину локального backlog, среднюю загрузку соседних узлов и индикатор отказа. В отличие от ранней версии прототипа backlog теперь учитывает не только ожидающие, но и уже исполняемые задачи. Дополнительно в наблюдение включаются четыре аукционных признака: нормированное число задач, рекомендованных аукционом данному узлу, средний уровень платежа по этим задачам, относительная нагрузка по CPU и backlog-aware отношение прогнозируемого времени завершения к дедлайнам.

В конец вектора наблюдения добавляется маска допустимых действий. Тем самым агент получает уже не абстрактное локальное состояние, а расширенное наблюдение, соответствующее гибридной Dec-POMDP-модели главы~4. При текущей конфигурации размер локального наблюдения составляет $13$ признаков: $5$ базовых, $4$ аукционных и $4$ бинарных индикатора допустимых действий.

Набор действий агента включает четыре варианта: принять рекомендованное назначение, отклонить его, повысить приоритет принятой задачи и перевести узел в безопасный режим \texttt{LOW}. В текущей реализации \texttt{LOW} не сводится к простому изменению метки приоритета: узел принимает только те задачи, для которых backlog-aware оценка всё ещё укладывается в допустимый интервал по дедлайну, а остальные задачи отклоняются. Маска допустимости задаёт подмножество действий, не нарушающих текущих ограничений. Например, для отказавшего узла допустимым остаётся только отклонение, а при отсутствии назначенных задач допустимым остаётся нейтральное действие.

\begin{lstlisting}[language=Python,caption={Формирование расширенного наблюдения},label={lst:observations}]
obs = np.concatenate(
    [
        np.array(
            [
                node.cpu_available / max(node.cpu_capacity, 1),
                node.memory_available / max(node.memory_capacity, 1),
                min((len(node.task_queue) + len(node.task_executed)) / 10.0, 1.0),
                neighbor_load,
                1.0 if node.is_failed else 0.0,
            ],
            dtype=np.float32,
        ),
        auction_features[node.id],
        action_masks[node.id],
    ]
)
\end{lstlisting}

\section{Интеграция QMIX}

Обучаемая часть построена в парадигме CTDE. Каждый агент использует рекуррентную сеть \texttt{GRUAgent}, которая аппроксимирует локальную Q-функцию по последовательности наблюдений. Индивидуальные значения Q затем объединяются в mixing network, формирующую глобальную функцию $Q_{tot}$ с сохранением свойства монотонности.

\begin{lstlisting}[language=Python,caption={Локальная сеть агента QMIX},label={lst:gru-agent}]
class GRUAgent(nn.Module):
    def __init__(self, obs_size: int, hidden_size: int, action_size: int):
        super().__init__()
        self.gru = nn.GRU(obs_size, hidden_size, batch_first=True)
        self.fc1 = nn.Linear(hidden_size, 64)
        self.fc2 = nn.Linear(64, action_size)
        self.relu = nn.ReLU()

    def forward(self, obs: torch.Tensor, hidden: torch.Tensor = None):
        if hidden is None:
            hidden = torch.zeros(
                obs.size(0),
                self.hidden_size,
                device=obs.device,
                dtype=obs.dtype,
            )
        gru_out, hidden = self.gru(obs, hidden.unsqueeze(0))
        gru_out = gru_out[:, -1, :]
        x = self.relu(self.fc1(gru_out))
        q_values = self.fc2(x)
        return q_values, hidden.squeeze(0)
\end{lstlisting}

В актуальной версии особое значение имеет выбор действий с учётом маски допустимости. Это относится как к онлайн-исполнению, так и к построению целевых действий на следующем шаге при вычислении TD-цели. Тем самым обучаемая политика не тратит опыт на действия, заранее противоречащие ресурсным или логическим ограничениям текущего раунда.

\begin{lstlisting}[language=Python,caption={Выбор действий с учётом маски допустимости},label={lst:select-actions}]
def select_actions(self, obs: np.ndarray) -> np.ndarray:
    actions = []
    with torch.no_grad():
        for i, agent_net in enumerate(self.agent_networks):
            obs_tensor = torch.FloatTensor(obs[i:i+1]).unsqueeze(0)
            q_values, _ = agent_net(obs_tensor)
            valid_actions = np.flatnonzero(self._extract_action_mask(obs[i]))

            if np.random.random() < self.epsilon:
                action = int(np.random.choice(valid_actions))
            else:
                mask_tensor = torch.BoolTensor(
                    self._extract_action_mask(obs[i])
                ).unsqueeze(0)
                action = int(
                    self._masked_argmax(q_values, mask_tensor).item()
                )
            actions.append(action)

    return np.array(actions)
\end{lstlisting}

\section{Гибридное командное вознаграждение}

Связь между аукционным и обучаемым контурами реализует класс \texttt{RewardManager}. Текущая реализация использует общий командный сигнал, одинаковый для всех агентов. Это соответствует постановке главы~3, в которой целевая функция обучения должна быть согласована с глобальной целью системы.

После серии валидационных запусков логика reward была уточнена в двух отношениях. Во-первых, глобальная часть сигнала стала backlog-aware: риск нарушения дедлайнов оценивается не только по времени обслуживания отдельной задачи, но и с учётом накопленного backlog на узле. Во-вторых, аукционная компонента не смешивается с RL-сигналом постоянно. Она активируется только в явно выраженном режиме перегрузки, то есть в те интервалы, когда среда фиксирует внешнее окно пикового входного потока. Это устраняет искусственный консерватизм, который возникал при постоянном положительном поощрении завершённых аукционных задач даже в спокойных режимах.

\begin{lstlisting}[language=Python,caption={Формирование гибридного командного reward},label={lst:reward-manager}]
def compute_global_reward(
    self,
    social_welfare,
    deadline_violation_rate,
    drop_rate,
    load_imbalance,
    fairness_index,
    gini_coefficient,
    backlog_pressure,
):
    sw_component = social_welfare / max(self.num_devices, 1)
    fairness_penalty = max(0.0, self.fairness_target - fairness_index)
    gini_penalty = max(0.0, gini_coefficient - self.gini_target)
    backlog_penalty = max(0.0, backlog_pressure)
    raw_reward = (
        sw_component
        - 0.9 * deadline_violation_rate
        - 0.8 * drop_rate
        - 0.6 * load_imbalance
        - 0.5 * backlog_penalty
        - fairness_penalty
        - gini_penalty
    )
    return float(np.tanh(raw_reward))

def combine_rewards(
    self,
    social_welfare,
    fairness_index,
    gini_coefficient,
    deadline_violation_rate,
    drop_rate,
    load_imbalance,
    completed_payments,
    completed_welfare,
    backlog_pressure,
    stress_context,
):
    global_reward = self.compute_global_reward(...)
    auction_reward = self.compute_auction_reward(
        completed_payments=completed_payments,
        completed_welfare=completed_welfare,
    )
    lambda_vcg = self.vcg_weight * np.clip(stress_context, 0.0, 1.0)
    hybrid_reward = (1.0 - lambda_vcg) * global_reward + lambda_vcg * auction_reward
    shared_reward = (1.0 - self.global_weight) * hybrid_reward + self.global_weight * global_reward
    return np.full(self.num_agents, shared_reward, dtype=float)
\end{lstlisting}

\section{Конфигурация прототипа и экспериментальный контур}

Все основные параметры вынесены в файл \texttt{src/config.py}. Это обеспечивает воспроизводимость экспериментов и позволяет варьировать как свойства среды, так и свойства обучения. В конфигурации задаются число устройств и узлов, параметры поступления задач, границы генерации CPU-, memory- и data-size требований, характеристики отказов, ценовые коэффициенты узлов, параметры перегрузки, а также гиперпараметры QMIX.

В ходе подготовки экспериментальной главы прототип был дополнен отдельным воспроизводимым benchmark-контуром. Класс \texttt{BenchmarkRunner} задаёт фиксированный набор из четырёх сценариев --- стабильная нагрузка, пиковая нагрузка, разнородные ресурсы и отказы узлов --- и сравнивает пять методов: MA--VCG, Heuristic-LoadAware, Random, QMIX и MA--VCG--QMIX. Существенная правка, сделанная после анализа ранних результатов, касается seed-протокола: теперь все методы внутри одного сценария прогоняются на одном и том же наборе seed, то есть на идентичных случайных экземплярах сети, потока задач и отказов. Это делает межметодное сравнение парно-сопоставимым и устраняет методологическое смещение, присутствовавшее в предыдущем варианте pipeline.

Отдельная точка входа \texttt{main\_run\_all\_scenarios.py} объединяет запуск benchmark-контура и последующий экспорт результатов. После завершения вычислений класс \texttt{ResultsVisualizer} строит сводные таблицы в формате \LaTeX\ и полный набор графиков для экспериментальной главы, сохраняет их в каталог \texttt{experiments/results} и при необходимости синхронизирует с деревом файлов диссертации. В частности, pipeline автоматически формирует как общую сводку, так и таблицу сценарных лидеров, причём при совпадении значений социального благосостояния явно отражает несколько со-лидирующих методов. Тем самым глава~6 опирается не на вручную подготовленные таблицы, а на автоматически воспроизводимую цепочку получения артефактов.

\section{Тестирование}

Для контроля корректности реализации предусмотрены четыре группы тестов. Тесты аукционного слоя проверяют форму распределения, неотрицательность платежей, корректность точного распределения при ресурсных ограничениях и правильный расчёт VCG-платежа по чистому вкладу участника. Тесты QMIX проверяют прямой проход нейросетевых компонентов и соблюдение масок допустимых действий. Интеграционный тест проверяет полный конвейер: формирование наблюдений, выбор действий, аукционный шаг среды, сохранение перехода в replay buffer и один шаг обучения. \section{Ограничения реализации}

Несмотря на более полное соответствие формальной модели, текущая версия прототипа остаётся исследовательским инструментом и сохраняет ряд ограничений:
\begin{itemize}
	\item точный поиск распределения ориентирован на сценарии малой и средней размерности и не претендует на промышленную масштабируемость;
	\item сетевой слой моделируется агрегированными задержками графа и не учитывает полный стек сетевого взаимодействия;
	\item выполнение задач описано через укрупнённую модель CPU, памяти и времени обслуживания без моделирования контейнеризации и реального системного планировщика;
	\item пространство локальных действий остаётся дискретным и включает только четыре интерпретируемых режима;
	\item аукционный контекст в наблюдениях представлен компактным набором агрегированных признаков, а не полной структурой глобального состояния.
\end{itemize}

Эти ограничения являются осознанными. Они позволяют сосредоточиться на главной исследовательской задаче: проверить, даёт ли объединение аукционного механизма и кооперативного MARL-подхода измеримый эффект по сравнению с использованием только одного из этих контуров.

\section{Выводы по главе}

Разработанный программный прототип реализует полный цикл работы метода MA--VCG--QMIX: от генерации задач и построения сетевой топологии до точного аукционного распределения, расчёта VCG-платежей, формирования расширенных наблюдений, выбора локальных действий и обучения кооперативной политики. Архитектура реализации непосредственно следует построенной в диссертации двухконтурной схеме, в которой аукционный слой формирует экономический контекст, а обучаемый слой использует его для адаптивного управления.

Наличие многосидового benchmark-запуска, автоматического сохранения результатов, средств визуализации и тестов делает прототип пригодным для воспроизводимой экспериментальной проверки.
